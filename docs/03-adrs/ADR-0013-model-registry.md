## Context

**Today, "which model runs a Step" and "how that model is invoked" are the same concept.** A Pipeline Step's `executor` field (`engine.Router.Resolve`) names an *Executor* — `project.ExecutorConfig.Vendor` plus `Model` together decide both *how* (which vendor package: `executor/openai`, `executor/geminicli`, ...) and *what* (which model string that package is given) in one `.foundry/executors.json` entry. There is no separate place that answers "what models exist, independent of how they're invoked" — e.g. "Gemini 3.5 Flash is a Google model, reachable via the `gemini` Executor" as a fact on its own, distinct from a specific project's own configuration choice.

**This repository's own recent configuration work makes the gap concrete.** `.foundry/executors.json`/`.foundry/config.json` now name four vendors across four different models (Gemini for planning, Claude Code for implementation, GPT via GitHub Models for review, Ollama for bugfixes — see [getting-started.md](../04-guides/getting-started.md)), each chosen for a specific reason. That reasoning — which model is which vendor's, which provider it belongs to, what it's called for a human reading a config file — lives only in prose (this ADR, getting-started.md, code comments), not in any structure Foundry itself could query or display.

**The maintainer's ask, verbatim in spirit:** introduce a `ModelRegistry` abstraction — distinguishing *Executor* (how a model is invoked: `claude-code`, `gemini-cli`, `ollama`, ...) from *Model* (what is executed: `claude-sonnet`, `gemini-2.5-pro`, `gpt-5.5`, ...), with each Model belonging to exactly one Executor — **as an abstraction only, with explicit, repeated constraints that this PR change no existing behavior**: no pipeline-parsing changes, no execution-flow changes, no migration, existing tests and configuration must keep working exactly as today. The registry should "simply exist and be injectable."

**This is deliberately narrower than, and does not reopen, two already-declined decisions.** [ADR-0006](ADR-0006-routing-and-policy.md) declined capability-based routing/negotiation until a real trigger fires; [ADR-0008](ADR-0008-extension-isolation-and-contract-versioning.md) declined a third-party extension mechanism until a real third party asks. A catalog of "which model belongs to which Executor" is metadata, not a routing policy. If a future PR wants to build capability-aware routing (matching a Step's declared *capability* requirements against advertised Executor properties, with negotiation or failover) on top of this catalog, that remains its own decision, gated on its own trigger, exactly as ADR-0006 already requires.

**Same-day amendment — a second increment.** The maintainer's direct follow-up request: let a Pipeline Step reference a Model directly (`{"model": "claude-sonnet"}`), not only an Executor pin, with explicit constraints again repeated: backward compatibility mandatory, `executor` keeps working, `model` is optional, model wins when both are set, unknown model fails validation, unknown executor keeps its existing behavior unchanged, no fallback, no routing beyond what already exists, no execution-semantics change. This is a deliberately small, deterministic extension of the *same* resolution `engine.Router.Resolve` already performs for `executor` — not new routing logic: a Model name is looked up once, translated into an Executor name, and that name is resolved exactly as an `executor` pin already was. It still does not reopen ADR-0006's declined capability-negotiation decision — there is no matching, scoring, or fallback of any kind here, only one more deterministic name-to-name lookup ahead of the pre-existing one.

**Same-day amendment — a third increment.** The maintainer's next follow-up request: expose per-model capability metadata (`supports`: `tool_use`, `thinking`, `streaming`, `multimodal`, `structured_output`; `limits`: `max_context`; `quality`: `reasoning`, `coding`, `review`), explicitly "not used yet — only expose it": no behavior changes, Registry-only. This is the same "expose now, consume later" shape the original abstraction already established for Executor/Model themselves — richer data on an already-inert catalog, not a new consumer of it. Nothing in `engine.Router.Resolve` reads any of these new fields; `Resolve`'s own logic (Decision 5 below) is untouched by this increment.

**Same-day amendment — a fourth increment.** The maintainer's next follow-up request: preferred model lists — a Step names an ordered `preferred` array (e.g. `["claude-opus", "claude-sonnet", "gemini-2.5-pro"]`) instead of a single `model`. Explicit behavior requested: "pick the first available model," but "do NOT implement availability checks yet — simply select the first item," maintaining backward compatibility, with no routing and no retries. Read literally: today, `preferred`'s only behavior is picking `preferred[0]` and resolving it exactly as `model` already resolves — the rest of the list is inert, carried only so a later, separately-decided increment can add real availability probing and fallback without another migration. This does not reopen ADR-0006's declined capability-negotiation decision, for the same reason the second increment didn't: there is still no matching, scoring, probing, or fallback — one more deterministic "pick a name, look it up" step ahead of the two that already existed.

**Same-day amendment — a fifth increment.** The maintainer's next follow-up request: a Model Health Manager — maintain runtime state per model (`AVAILABLE`, `UNAVAILABLE`, `COOLDOWN`, `UNKNOWN`, plus `reason`/`retryAt` metadata), explicit requirements: no automatic failover, no routing, the Registry queries the health manager, an Executor can update it, tests required, no Pipeline changes. This is the natural next "expose now, consume later" slice: `Preferred`'s own fourth-increment gap (no real availability awareness) is exactly what a health signal would eventually inform, but this increment stops short of connecting the two — it only builds the runtime state store and the Registry's read-only query path onto it. `engine.Router.Resolve` is completely untouched by this increment; nothing about it reads a `HealthManager` in any way.

**Same-day amendment — a sixth increment, and the first real execution-semantics change.** The maintainer's next follow-up request: implement automatic model failover — supported only when `preferred[]` is configured; a current model failing because of rate limit, temporary unavailability, or timeout should select the next compatible model in the list; authentication, invalid-model, and unsupported-capability failures must never fail over; every switch must be logged; tests required; backward compatibility mandatory. Unlike every increment before it, this one deliberately changes what happens during `Execute` — a generate Step with `preferred` naming more than one model can now genuinely retry against a second model within the same Step, something the fourth increment explicitly deferred ("do NOT implement availability checks yet") and the fifth explicitly declined to wire up ("no automatic failover"). Both of those increments' own stated limitations remain honestly named in their own Decision entries below — this increment closes exactly the gap they named, no more: it does not add real availability *probing* (there is still no check of whether a model is reachable before trying it — a failure is still only detected by actually attempting the call and it failing), does not consult `HealthManager` at all (the health signal and this failover decision remain two separate, unconnected mechanisms — a model reported `StatusUnavailable` via `Report` still isn't skipped preemptively; failover only reacts to a real, just-happened `Execute` failure), and does not implement capability-based *matching* against a Step's declared requirements (ADR-0006's own declined scope) — "select the next compatible model" is read here as "the next Preferred entry that successfully resolves," not a new negotiation mechanism.

## Decision

1. **New package `model`** (`model/registry.go`) defines `Info` (`ID`, `Executor`, `Provider`, `DisplayName`) and `Registry` (`NewRegistry`, `Register`, `Get`, `List`, `ByExecutor`) — a plain in-memory catalog, no persistence, no I/O, no dependency on any other Foundry package. `Register` refuses an empty ID, an empty Executor, or a duplicate ID (even under a different Executor) — each Model belongs to exactly one Executor, per the maintainer's own stated design.

2. **Executor packages that already have a natural, confident list of model IDs expose it via their own `SupportedModels() []model.Info`**: `executor/claude` (Anthropic's Claude models — informational only, since `executor/claude.Execute` has no model-selection parameter of its own today, unlike `executor/geminicli`/`executor/copilotcli`), `executor/geminicli` (Google's Gemini models, reusing `executor/gemini`'s own existing price-table model names — registered once, under the `"gemini"` Executor, per Decision 1's one-Executor-per-Model rule, not duplicated under `"gemini-api"`), `executor/openai` (both `"openai"`'s own hosted models and a couple of already-referenced `"openai-compatible"` examples: Ollama's `llama3`, GitHub Models' `openai/gpt-4.1` — this repository's own `.foundry/executors.json`/`.foundry/config.json`), and `executor/copilotcli` (a single informational `"copilot-default"` entry — no confirmed, documented list of selectable model IDs for the Copilot CLI's own `--model` flag exists to catalog honestly).

3. **`cmd/foundry`'s `buildModelRegistry()`** (`cmd/foundry/model_registry.go`) is the one place that calls every `SupportedModels()` and assembles one `*model.Registry` — mirroring why `cmd/foundry/main.go` is already the only place that imports every concrete Executor package (`project`/`cmd/foundry/commands` stay vendor-agnostic, per [ADR-0005](ADR-0005-executor-contract-and-capability-model.md)'s existing seam). Built once per process in `run()` and now threaded to every real entry point (see Decision 5) — no longer merely constructible-but-unused, as it was at this ADR's original drafting.

4. **`engine.Step`/`StepDocument` gain a new optional `Model string` field** (`json:"model,omitempty"`), decoded and validated exactly like every other additive Step field ([ADR-0004](ADR-0004-reusable-act-template-format-and-evolution-policy.md)'s already-accepted evolution policy — no separate ADR needed for the field itself, the same way `feeds_forward`/`target` needed none when they were added). A document that omits it, or predates it, decodes identically to before.

5. **`engine.Router` gains an optional `model.Registry`** (`WithModels`, returning a modified copy — the same value-type-copy pattern `NewRouter` itself already uses, not a new mutable-state mechanism) and a small, deterministic extension to `Resolve`: if `step.Model` is set, it is looked up in the attached Registry to find its Executor name, which then replaces `step.Executor` for the rest of `Resolve`'s existing, completely unchanged logic (registry lookup by name, or the default if the name is empty). Concretely:
   - **`model` wins when both are set** — Decision made explicit by the maintainer; no ambiguity, no merge, no negotiation between the two.
   - **Unknown model fails validation** — a `step.Model` not found in the attached Registry (or a Router with no Registry attached at all) is a clear, named error from `Resolve`, never a silent fallback to `step.Executor` or the default.
   - **Unknown executor is unchanged** — whether the name being resolved came from `step.Executor` directly or from a resolved Model's Executor, an unregistered name fails exactly as `Resolve` already failed before this Decision existed; no new behavior was added to that path.
   - **No fallback, no new routing, no execution-semantics change** — once a name is decided (from Model or Executor), it is resolved through the exact same `ExecutorRegistry.Get` call as always; nothing about how the resulting `engine.Executor` is invoked, budgeted, or recorded changes.
   - A **known limitation, stated plainly rather than smoothed over**: a Model's Executor value is the *vendor* string (`"gemini"`, `"claude"`, `"openai"`, ...), which must match a project's own chosen *name* for a registered Executor in `.foundry/executors.json` for resolution to succeed (e.g. an entry literally named `"gemini"`, not `"planner"` built from vendor `"gemini"`). Models whose Executor is `"claude"` can never resolve today, since Claude Code is Foundry's implicit default and is never constructed through the named registry at all — this fails as "unknown executor," which is correct, deterministic behavior per the rule above, not a bug, but it is a real, named gap for a future increment to address (e.g. letting a project's own `.foundry/executors.json` name an entry after a bare vendor string) — explicitly out of scope here per "do not implement fallback, do not implement routing."

6. **`session.Session` gains `SetModelRegistry` (optional, mirrors `SetTicketFetcher`'s own post-construction attachment) and `cmd/foundry/commands`'s `Do`/`Resume`/`wireEngine` gain an optional trailing `models ...*model.Registry` parameter** (the same variadic zero-or-one shape `newNamedExecutor` already established for `session.NewSession`) — both wire `Router.WithModels` into the Router each already builds. `cmd/foundry/main.go`'s `run()` builds one `*model.Registry` via `buildModelRegistry()` and passes it to every real entry point (interactive session, `do`, `resume`). No existing call site of `session.NewSession` needed to change (the setter is additive); the handful of `wireEngine`/`Do`/`Resume` call sites (all within `cmd/foundry`) needed no changes either, since the new parameter is trailing and variadic.

7. **`model.Info` gains three new struct fields — `Capabilities`, `Limits`, `Quality`** (`model/registry.go`), each a small, explicit, comparable struct (not a `[]string`/`map`, which would have made `Info` itself non-comparable and broken `Registry`'s existing plain `==` equality tests): `Capabilities{ToolUse, Thinking, Streaming, Multimodal, StructuredOutput bool}`, `Limits{MaxContext int}`, `Quality{Reasoning, Coding, Review int}` on a hand-assigned 1 (weakest) to 5 (strongest) scale. All three are pure data with zero behavior: `Register`/`Get`/`List`/`ByExecutor` treat them exactly like every other `Info` field, and nothing in `engine.Router.Resolve` or anywhere else reads them. Every existing `Info` literal across the codebase (every `SupportedModels()` written before this increment, every test) keeps compiling and behaving identically, since Go's zero values for these new fields (`false`, `0`) are exactly "not rated" — never a different default that would change what an already-written entry means. `executor/claude`, `executor/geminicli`, and `executor/openai`'s `SupportedModels()` were updated to populate real, hand-curated values for every entry (the same "will drift, not vendor-confirmed" caveat their own price tables already carry); `executor/copilotcli`'s single `copilot-default` entry deliberately keeps all three fields at their zero value, since its underlying model is not confirmed — rating an unknown model would be worse than not rating it at all.

8. **`engine.Step`/`StepDocument` gain a new optional `Preferred []string` field** (`json:"preferred,omitempty"`), an ordered list of Model IDs. `Router.Resolve`'s precedence becomes: `Preferred[0]` (if `Preferred` is non-empty) wins over `Model`, which still wins over `Executor` — a strict extension of Decision 5's existing two-tier precedence, not a replacement of it. Concretely:
   - **Only `Preferred[0]` is ever consulted.** No availability probing of any kind, no iteration to a second entry, no retry — exactly the maintainer's own stated scope ("do NOT implement availability checks yet — simply select the first item"). The remaining entries are inert data today.
   - **An empty (`[]`) or absent `Preferred` falls through to `Model` exactly as before this field existed** — the same additive, zero-value-compatible pattern every prior Step field followed; `len(step.Preferred) > 0` is the only condition that activates this path at all.
   - **`Preferred[0]` unresolvable behaves exactly like an unresolvable `Model`** — a clear, named error naming the specific unregistered ID (`preferred[0]` in the error's own wording, distinguishing it from a plain `model` failure), never a fallback to the list's second entry, to `Model`, to `Executor`, or to the default.
   - This is the increment's own explicit "no routing, no retries" constraint, applied literally: `Preferred` today is syntactically richer than `Model` but behaviorally identical to writing `model: Preferred[0]` directly — the list exists so a future, separately-decided increment (real availability checking) has a place to add real fallback logic without a second Step-schema migration.

9. **New `model.Status`/`Health`/`HealthManager`** (`model/health.go`, same `model` package): `Status` is a string enum (`StatusAvailable`, `StatusUnavailable`, `StatusCooldown`, `StatusUnknown`); `Health{Status, Reason string, RetryAt time.Time}` is one model's current runtime health; `HealthManager` is an in-memory, mutex-protected `map[string]Health` with `Report(id string, health Health) error` (refuses an empty id, otherwise unconditionally overwrites — no enforced state-machine transitions) and `Get(id string) Health` (returns `Health{Status: StatusUnknown}` for anything never reported, never an error). This is a deliberately separate component from `Registry`'s own static catalog (`Info`/`Capabilities`/`Limits`/`Quality`): health is mutable, observed runtime state; catalog metadata is fixed and hand-curated. `Registry` gains `SetHealthManager` (optional attachment, mirroring `Router.WithModels`'s own pattern) and `Health(id string) Health`, a pure delegation to the attached `HealthManager` (or `Health{Status: StatusUnknown}` if none is attached) — satisfying "the Registry queries the health manager" literally, without `Registry` tracking health state itself. `Health` does not require `id` to be a `Register`-ed model — health tracking is independent of catalog membership, a deliberate design choice, not an oversight. "Health manager can be updated by executors" is satisfied as a capability (`HealthManager.Report` is a plain, public method any caller could invoke) — this increment does **not** wire any real `executor/*` package to call it automatically on every `Execute`; doing so would be a real behavior change (a new dependency an Executor would need injected, and a new side effect on every real run) well beyond "no automatic failover, no routing, no Pipeline changes." `engine.Router.Resolve` reads nothing from `HealthManager` or `Registry.Health` — a model reported `StatusUnavailable` is not skipped, retried elsewhere, or treated any differently by `Resolve` today. (Decision 10 below implements failover, but deliberately does not connect it to `HealthManager` — see its own scope note.)

10. **New `model.FailureClass`/`FailureError`/`ClassifyFailure`** (`model/failure.go`) and a rewritten generate-Step execution path (`engine/failover.go`'s `executeGenerateStep`, called from `engine/strategy.go`'s `runSteps` in place of its previous single Resolve/estimate/charge/Execute sequence) implement automatic failover:
    - `FailureClass` is a string enum with six named values — `FailureRateLimit`/`FailureTemporaryUnavailable`/`FailureTimeout` (retryable) and `FailureAuthentication`/`FailureInvalidModel`/`FailureUnsupportedCapability` (never retryable) — plus a `Retryable() bool` method. Any class not named above, and the absence of a class at all, both default to *not* retryable: failover is the exception a caller must explicitly classify into, never the default for an error this package doesn't recognize.
    - `FailureError{Class, Err}` (with `Error()`/`Unwrap()`) is how a caller marks a specific error as classified; `ClassifyFailure(err) (FailureClass, bool)` extracts it via `errors.As` (finding it anywhere in a wrap chain). No existing `executor/*` package is modified to emit a `FailureError` in this increment — the classification mechanism exists and is fully tested via fakes, but wiring a *specific* real vendor's HTTP status codes (or CLI exit behavior) to specific `FailureClass` values is a separate, real per-vendor mapping decision this increment does not make; every real Executor's error-returning behavior is completely unchanged.
    - `engine.Router` gains `ResolveModel(id string) (Executor, error)` — the same Model→Executor lookup `Resolve` already performs internally for `Model`/`Preferred[0]`, exposed standalone so the failover loop can resolve each subsequent `Preferred` entry in turn. `Resolve` itself is untouched — `ResolveModel` is purely additive, new code alongside it.
    - `executeGenerateStep` replaces `runSteps`' inline generate-Step body. **When `step.Preferred` has zero or one entries, its behavior is byte-for-byte identical to the pre-increment code** — one `Resolve`, one estimate, one charge, one `Execute`, immediate failure on any error — proven by every pre-existing engine test passing unchanged with no test modifications required. **When `step.Preferred` has two or more entries**: the first entry is resolved and tried via the normal `Resolve` path; if `Execute` fails and `model.ClassifyFailure` reports a retryable class, the next `Preferred` entry is resolved via `ResolveModel` and tried instead, after calling `reportFailover` to log the switch (satisfying "log every switch," e.g. "Claude Sonnet unavailable. Switching to Gemini 3.1 Pro."); any non-retryable or unclassified failure, or the last entry itself failing, fails the Step immediately with no further attempt. Cost estimation and Budget charging happen once per actual `Execute` call, including retries — a different model can have a genuinely different cost, so each attempt is estimated and charged on its own terms.
    - `reportFailover`/`FailoverReporter` is a new *optional* Reporter extension (`type FailoverReporter interface { ModelFailover(stepID, from, to string, class model.FailureClass, cause error) }`), deliberately **not** added as a new required method on `Reporter` itself — doing so would force every existing implementation (`cli.ProgressReporter`, `engine.SlogReporter`, `MultiReporter`, `noopReporter`, and every test fake) to gain the method just to keep compiling. A type assertion (`reporter.(FailoverReporter)`) is checked at the one call site; a Reporter that doesn't implement it (every one that existed before this increment) simply never receives failover narration, with zero code changes required anywhere else. Neither `cli.ProgressReporter` nor `engine.SlogReporter` was updated to implement it in this increment — narrating a failover to a real human/log stream is a real, separate follow-up, not required to satisfy "log every switch" at the mechanism level (a test fake proves the hook fires correctly).
    - **"Select the next compatible model" is read as "the next `Preferred` entry that successfully resolves,"** not a new capability-matching mechanism — this does not reopen ADR-0006's declined capability-based negotiation. **`HealthManager` (Decision 9) is deliberately not consulted anywhere in this path** — failover reacts only to a real, just-attempted `Execute` failure; it never preemptively skips a `Preferred` entry because `Registry.Health` reports it unavailable. Connecting the two remains a real, separate, not-yet-made decision.

## Consequences

- **Positive:** "what models exist, and which vendor runs them" is now a queryable fact independent of any one project's configuration, closing the prose-only gap this ADR's Context describes — a Pipeline document can now say `{"model": "claude-sonnet-5"}` (or an ordered `{"preferred": [...]}`) and have that actually mean something at Resolve time, not merely be catalogued, each catalogued entry now carries real capability/limit/quality data, a model's observed runtime health can now be reported and queried at all, and — the sixth increment's own real, working payoff — a generate Step naming two or more `preferred` models now genuinely survives a rate-limit/temporary-unavailable/timeout failure by trying the next one, with every switch logged. A later PR (a `foundry models` listing command, richer `executors.json` validation against known IDs, letting a bare vendor string resolve without a same-named registry entry, connecting `HealthManager` to failover so a known-unavailable model is skipped preemptively rather than only reactively, real per-vendor `FailureClass` classification in `executor/openai`/`executor/gemini`/etc., or capability-aware routing once ADR-0006's trigger fires) has a real starting shape instead of inventing one from scratch.
- **Cost:** a new package's worth of surface area (plus `engine/failover.go`) to maintain; `SupportedModels()` lists (now including their capability/limit/quality data) are static and hand-curated (not fetched from any vendor's live model-listing API), so they will drift out of date as vendors ship new models or revise documented limits — no different in kind from `executor/openai`'s/`executor/gemini`'s own existing hand-maintained price tables, which carry the identical staleness risk already. A Pipeline author can now write a `model` (or `preferred[0]`) that resolves to a vendor with no same-named `.foundry/executors.json` entry (notably `"claude"`, see Decision 5's stated limitation) and get a clear "unknown executor" error rather than it actually working — a real, if honestly-documented, rough edge until a future increment addresses it. Automatic failover only actually helps once a real Executor package is updated to emit a classified `FailureError` — with none updated in this increment, `preferred[]`'s failover behavior is fully implemented and tested but dormant against every real vendor today, exactly as honestly stated in Decision 10. `HealthManager` (Decision 9) and failover (Decision 10) remain two disconnected mechanisms by design — a model `Report`-ed `StatusUnavailable` is still never preemptively skipped; failover only ever reacts to a real, just-attempted failure.
- **Harder:** none identified — every change here is additive except the generate-Step execution path itself (Decision 10's `executeGenerateStep`), and that change is proven behavior-preserving for every Step that doesn't configure two-or-more-entry `preferred` by the full pre-existing test suite passing with zero test modifications; reverting any of the six increments (the `Model` field and `Router.WithModels`; the `Capabilities`/`Limits`/`Quality` fields; the `Preferred` field; `HealthManager`/`Registry.Health`; failover/`FailureClass`/`ResolveModel`/`FailoverReporter`; or the whole `model` package) would have zero effect on any Pipeline that never sets `model`/`preferred` with two-or-more entries, which is every Pipeline document in this repository and every existing test.

## Migration Strategy

Original drafting: none — pure addition, no existing file's logic touched. Amendments two through five: also none requiring action from an existing project — `model`/`preferred` are optional and `executor`-only Pipelines are byte-for-byte unaffected; the new `Info` fields default to zero ("not rated") for any entry that doesn't set them; a `Registry` with no `HealthManager` attached answers `Health` queries as unknown rather than erroring. The sixth amendment (failover) required rewriting `runSteps`' generate-Step case in `engine/strategy.go` into a call to `executeGenerateStep` (`engine/failover.go`) — a real code change to an existing file's control flow, not purely new files — but is proven behavior-preserving for the zero/one-`preferred`-entry case (every existing case) by the complete pre-existing engine test suite passing unchanged, with no test needing modification to keep passing. `go build ./...`, `go vet ./...`, and `go test -race ./...` all pass across all six increments, with new files (`model/failure.go`, `engine/failover.go`, and their own `_test.go` files) plus new, additive lines in a small, named set of existing files (`engine/step.go`, `engine/document.go`, `engine/router.go`, `engine/strategy.go`, `session/session.go`, `cmd/foundry/commands/do.go`, `cmd/foundry/commands/resume.go`, `cmd/foundry/main.go`, `model/registry.go`, `model/health.go`, and each `executor/*/models.go`).

## Review Checklist

- [ ] Maintainer confirms the `Info{ID, Executor, Provider, DisplayName, Capabilities, Limits, Quality}` shape and the "each Model belongs to exactly one Executor" rule match the intended abstraction.
- [ ] Maintainer confirms the Model-wins-over-Executor precedence, the unknown-model/unknown-executor validation split, and the stated "claude vendor can never resolve via Model yet" limitation are all acceptable as this increment's scope, not gaps to close before ratifying.
- [ ] Maintainer confirms the `Capabilities`/`Limits`/`Quality` shape (booleans for `supports`, `MaxContext` for `limits`, a 1–5 scale for `quality`) matches what was asked, and that hand-curated (not vendor-confirmed) values are an acceptable starting point.
- [ ] Maintainer confirms `Preferred[0]`-only resolution (no availability check, no fallback to a later entry) was the correct scope for the fourth increment at the time, now superseded for the 2+-entry case by Decision 10's actual failover — the fourth increment's own behavior stands unchanged for a single-entry `Preferred`.
